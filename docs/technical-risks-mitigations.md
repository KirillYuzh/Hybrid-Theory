## 1. Система отчётности KYT-движка

KYT-движок генерирует три типа отчётных документов: 
- операционные, 
- регуляторные
- аналитические

Все отчёты строятся на основе единого слоя данных (Iceberg + Kafka) и доступны через API и BI-дашборды.

### 1.1. Операционные отчёты (внутренние)

| Отчёт | Периодичность | Содержание |
|-------|---------------|------------|
| **Ежедневный свод по транзакциям** | Ежедневно | Общий объём, распределение по скорам (GREEN/YELLOW/RED), количество холдов, эскалаций |
| **Отчёт по просроченным SLA** | Ежедневно | Транзакции, где время рассмотрения превысило нормативы (1/150 ставки ЦБ) |
| **Нагрузка на инфраструктуру** | Каждый час | TPS, latency (p95), загрузка GPU/CPU, очередь в Kafka |
| **Инциденты reorg/rollback** | Ad-hoc | Список транзакций, подвергшихся откату блокчейна, и принятые меры |

**Формат:** JSON + Parquet (для аналитики), PDF (для руководства)

### 1.3. Аналитические отчёты (для ML-команды)

| Отчёт | Периодичность | Содержание |
|-------|---------------|------------|
| **Метрики модели** | Ежедневно | Precision/Recall/F1 по классам, AUC-PR, FPR, False Clean Rate |
| **Drift detection** | Еженедельно | PSI по признакам, падение AUC-PR > 0.02 → триггер переобучения |
| **Shadow Mode сравнение** | Еженедельно | Расхождение между автоматическим скором и решением аналитика |
| **Active Learning фидбеки** | Ежемесячно | Улучшение метрик после N фидбеков |

## 2. Технические риски и их митигации

### 2.1. Reorg и Rollback

Блокчейн подвержен откату блоков (2–3 блока в Ethereum, 6 в Bitcoin). Транзакция может быть оценена как рисковая, а затем исчезнуть из финальной цепочки.

**Решение:** watermarking (номер блока + глубина подтверждений) + eventual consistency. Решения принимаются после 6 подтверждений. При reorg — откат фич в Iceberg через time travel, пересчёт скора, отмена блокировок.

**SLA:** обнаружение reorg — 30 сек, откат — 5 мин, пересчёт — 10 мин.

### 2.2. Fallback при отказе TGN

TGN (Temporal Graph Network) — ресурсоёмкая модель. При нагрузке >50 TPS может не успевать.

**Решение:** два пути. Fast path — LightGBM на CPU (<50 мс). При успехе — финальный скор. При сбое TGN — предварительный скор через LightGBM, TGN-скор обновляется асинхронно (до 5 минут). Если обе модели недоступны — FAIL-CLOSED, транзакция холдится.

### 2.3. OpenSanctions: качество данных

- Из 1.2M сущностей в OpenSanctions только 148 криптоадресов (0.012%)
- Обновление hourly — возможна задержка до 1 часа
- Ложные срабатывания при совпадении адресов

**Решение:** external signal имеет вес 0.15 в ансамбле. Ложное срабатывание OpenSanctions не блокирует транзакцию — комбинируется с LGBM (0.50), K-Score (0.20), VAE (0.15). Для неизвестных адресов risk_score по умолчанию = 0.5.
