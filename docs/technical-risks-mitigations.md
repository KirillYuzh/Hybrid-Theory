## Блок 24.2: Юридическая модель

### 1.1. Кто подписывает решение о блокировке

#### Принцип: Human-in-the-Loop для всех блокирующих решений

KYT-система **не принимает автономных решений** о блокировке средств клиентов. Это критически важно для соблюдения:

- **115-ФЗ «О противодействии легализации доходов...»** — требует документального обоснования решений
- **Гражданского кодекса РФ** — ст. 845, 847: ограничение распоряжения средствами только по закону или договору
- **Судебной практики** — незаконная блокировка влечёт административную ответственность и гражданско-правовые санкции

#### Матрица подписания решений

| Тип транзакции | Автоматическое действие | Требуемое одобрение | Кто подписывает |
|----------------|------------------------|---------------------|-----------------|
| **GREEN** (< 0.3) | Пропуск без ограничений | Не требуется | — |
| **YELLOW** (0.3–0.7) | Помещение в очередь на review | Не требуется для прохождения | — |
| **RED** (> 0.7) | **ХОЛД** (приостановка исполнения) | **Обязательно** | Комплаенс-офицер уровня L2+ |
| **RED + External Hit** (OFAC/Санкции) | **Блокировка** | **Обязательно** | Руководитель подразделения комплаенс (L3) + уведомление Росфинмониторинга |
| **Подозрение нарупшение 115-ФЗ** | **Блокировка + Эскалация** | **Обязательно** | Chief Compliance Officer (CCO) |

#### Ролевая модель

```
┌─────────────────────────────────────────────────────────────┐
│                    РОЛЕВАЯ МОДЕЛЬ ПОДПИСАНИЯ                │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  L1: Комплаенс-аналитик                                     │
│  ├── Подписание решения по YELLOW (мониторинг)               │
│  └── Запрос дополнительных документов у клиента              │
│                                                              │
│  L2: Старший комплаенс-офицер                               │
│  ├── Подписание решения о ХОЛД для RED-транзакций           │
│  ├── Снятие ХОЛД после рассмотрения                         │
│  └── Передача в L3 при подтверждении нарушения              │
│                                                              │
│  L3: Руководитель подразделения комплаенс                    │
│  ├── Подписание решения о блокировке                         │
│  ├── Направление уведомлений в Росфинмониторинг              │
│  └── Согласование разблокировки                             │
│                                                              │
│  CCO: Chief Compliance Officer                               │
│  ├── Операционный контроль всей системы                     │
│  ├── Утверждение изменений в порогах скоринга              │
│  └── Взаимодействие с регулятором                          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

#### Audit Trail

Каждое решение должно содержать:

1. **Идентификатор транзакции** (tx_id, tx_hash)
2. **Дата и время решения**
3. **Автоматический скор** (P_risk, K-Score, компоненты)
4. **Роль и ФИО подписанта**
5. **Тип решения** (ХОЛД / БЛОКИРОВКА / ОТКЛОНЕНО / ПРОПУЩЕНО)
6. **Обоснование** (свободный текст или выбор из справочника)
7. **Документы**, приложенные к решению
8. **Результат** (разблокировано / остаётся заблокированным / эскалация)

### 1.2. SLA по разблокировке

#### Регуляторные требования

**Ключевые нормы:**

1. **Ст. 7 115-ФЗ**: Операции подлежат обязательному контролю, банк вправе отказать в проведении операции
2. **Ст. 13.27 КоАП РФ**: Нарушение законодательства о противодействии легализации — штрафы
3. **Судебная практика**: Необоснованная блокировка — возмещение убытков + проценты по ст. 395 ГК РФ

#### Штрафные санкции за незаконную блокировку

| Параметр | Значение | Источник |
|----------|----------|----------|
| **Ставка ЦБ** | Текущая ключевая ставка ЦБ РФ | cbr.ru |
| **Расчёт штрафа** | 1/150 ставки ЦБ за каждый день | Судебная практика |
| **Пример (ставка 18%)** | 0.12% в день от суммы | 43.8% годовых |
| **Верхний предел** | Не ограничен | Решение суда |

#### SLA Matrix

| Категория | Максимальное время | Действие при превышении |
|-----------|-------------------|------------------------|
| **Разблокировка после запроса документов** | 1 рабочий день | Автоматическая разблокировка + эскалация L2 |
| **Рассмотрение ХОЛД транзакции** | 3 рабочих дня | Обязательный пересмотр L3 |
| **Снятие ХОЛД после предоставления документов** | 1 рабочий день | Штрафные санкции (1/150 ставки ЦБ) |
| **Эскалация на CCO** | 5 рабочих дней | Обязательное решение + уведомление регулятора |
| **Разблокировка ошибочно заблокированной транзакции** | 24 часа с момента выявления | Полное возмещение + проценты |

#### Автоматизированные эскалации

```
День 0: ХОЛД наложен (RED-скор)
    │
    ▼
День 1: Автоматический reminder комплаенс-офицеру L2
    │
    ▼
День 2: Если не рассмотрено → эскалация руководителю L3
    │
    ▼
День 3: Если не рассмотрено → уведомление CCO + автоблокировка разблокировки
    │
    ▼
День 5: Если не рассмотрено → уведомление в Росфинмониторинг о проблеме
```

#### Метрики для мониторинга SLA

| Метрика | Целевое значение | Критическое |
|---------|------------------|-------------|
| **Среднее время разблокировки** | < 24 часов | > 48 часов |
| **Доля своевременно рассмотренных ХОЛД** | > 95% | < 90% |
| **Процент эскалаций** | < 5% | > 10% |
| **Стоимость штрафов за период** | 0 | > $10k/мес |

### 1.3. Согласование с Росфинмониторингом

#### Регуляторная база

1. **115-ФЗ «О противодействии легализации доходов...»** — основной закон

|--------|------------------------|--------|

| **Порядок эскалации** | Согласовать регламент | ❌ Не согласовано |

#### Порядок действий при автоблокировке (сценарий)

```
СЦЕНАРИЙ: RED-транзакция + автоматическая блокировка

00:00   Транзакция получает RED-скор (> 0.7)
        → Автоматический ХОЛД наложен
        → Уведомление в систему комплаенс-очереди

00:05   Email/SMS уведомление комплаенс-офицеру L2
        → Кейс добавлен в очередь review

00:30   Если не назначен → эскалация руководителю L3

24 ч.   Если не рассмотрено:
        → Автоматическая разблокировка (SLA!)
        → Логирование инцидента

48 ч.   Обязательная эскалация на CCO
        → Решение об оставлении блокировки или разблокировке

72 ч.   Если блокировка остаётся:
        → Направление уведомления в Росфинмониторинг
        → Формат: Электронное сообщение (см. раздел 1.4)

5 раб.дней:   Если не урегулировано:
        → Уведомление регулятора о споре
        → Возможная эскалация в ЦБ
```

## Shadow Mode

### Цель

Shadow Mode позволяет протестировать KYT-систему на реальном трафике **без принятия решений**, минимизируя юридические риски до начала production.

### Параметры Shadow Mode

| Параметр | Значение | Обоснование |
|----------|---------|-------------|
| **Длительность** | 3–6 месяцев | Достаточно для накопления статистики по FP-rate |
| **Режим** | Параллельный | Все транзакции проходят через KYT + старый процесс |
| **Блокировки** | ОТКЛЮЧЕНЫ | Система только логирует, но не действует |
| **Критерии перехода в Production** | FP-rate < 15%, совпадение с комплаенс > 99% | Статистически значимая выборка |

### Критерии выхода из Shadow Mode

```
┌─────────────────────────────────────────────────────────────────┐
│                    КРИТЕРИИ ПЕРЕХОДА В PRODUCTION               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. FP-rate (False Positive Rate)                               │
│     └─ Определение: заблокировано системой, признано            │
│        комплаенсом как "ложная тревога"                         │
│     └─ Целевое значение: < 15%                                 │
│     └─ Минимальная выборка: 1000 RED-транзакций                 │
│                                                                  │
│  2. Precision на RED-категории                                  │
│     └─ Целевое значение: > 85%                                 │
│     └─ Определение: доля реальных нарушений среди RED           │
│                                                                  │
│  3. Recall на известных паттернах                               │
│     └─ Целевое значение: > 95%                                 │
│     └─ Тестируется на historical ground truth                   │
│                                                                  │
│  4. Совпадение с решениями комплаенс                           │
│     └─ Целевое значение: > 99%                                  │
│     └─ Сравнение: KYT-решение vs решение аналитика              │
│                                                                  │
│  5. Согласование с Росфинмониторингом                          │
│     └─ Получение официального одобрения                          │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### Логирование в Shadow Mode

Все транзакции логируются с полной информацией:

```
ShadowLog {
    tx_id: string,
    timestamp: datetime,
    auto_score: float,
    auto_zone: "GREEN" | "YELLOW" | "RED",
    auto_triage: "AUTO_CLOSE" | "PRIORITY" | "ESCALATION",
    manual_decision: string | null,      // Решение аналитика (после)
    manual_correct: boolean | null,       // Было ли авто-решение верным
    discrepancy: boolean,                 // Было ли расхождение
    discrepancy_reason: string | null,    // Причина расхождения
}
```

## Reorg и Rollback

### Проблема

Блокчейн (Ethereum, Bitcoin) подвержен **reorganization** — откату блоков на 2–3 блока. Это критично для KYT-системы, где транзакция может быть посчитана как "плохая" и заблокирована, а затем её не окажется в финальной цепочке.

### Решение: Watermarking + Eventual Consistency

```
┌─────────────────────────────────────────────────────────────────┐
│                         REORG HANDLER                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. WATERMARKING                                                │
│     ├─ Каждая транзакция помечается номером блока               │
│     └─ Фичи вычисляются с учётом глубины (confirmations)        │
│                                                                  │
│  2. ROLLBACK MECHANISM                                          │
│     ├─ При обнаружении reorg:                                    │
│     │  ├─ Откат фич в Iceberg (time travel)                     │
│     │  ├─ Пересчёт риск-скора                                   │
│     │  └─ Отмена блокировок, если tx не в main chain            │
│     └─ Глубина отката: 3 блока (Ethereum), 6 блоков (Bitcoin)  │
│                                                                  │
│  3. EVENTUAL CONSISTENCY                                        │
│     ├─ Решения принимаются после 6 confirmations                │
│     └─ Финальная блокировка — только для подтверждённых tx      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### SLA для обработки Reorg

| Этап | Максимальное время |
|------|-------------------|
| Обнаружение reorg | 30 секунд (мониторинг блоков) |
| Откат фич в Iceberg | 5 минут |

## Fallback-архитектура

### Проблема производительности TGN

Temporal Graph Network (TGN) — ресурсоёмкая модель. При высокой нагрузке (> 50 TPS) она может не успевать, что создаёт риск пропуска транзакций.

### Fallback-схема

```
┌─────────────────────────────────────────────────────────────────┐
│                      FALLBACK ARCHITECTURE                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  TRANSACTION IN ─────────────────────────────────────────────►││
│       │                                                         │
│       ▼                                                         │
│  ┌─────────────┐     Успех      ┌─────────────┐                 │
│  │   TGN       │────────────────►│   RISK      │                 │
│  │  (GPU)      │                │  CALCULATION│                 │
│  └─────────────┘                └─────────────┘                 │
│       │                          (LightGBM)                      │
│    Сбой│                                                        │
│       ▼                                                         │
│  ┌─────────────┐     Fallback    ┌─────────────┐                 │
│  │  LightGBM   │────────────────►│  ASYNC TGN  │                 │
│  │  (CPU)      │  (50ms)        │  update (5m)│                 │
│  └─────────────┘                └─────────────┘                 │
│                                                                  │
│  ═══════════════════════════════════════════════════════════════│
│  EVENTUAL CONSISTENCY:                                          │
│  ├─ Решение принимается по LightGBM (fast path)                │
│  ├─ TGN-скор обновляется асинхронно                            │
│  └─ Если TGN меняет оценку — новое решение через 5 минут        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### SLA для Fallback

| Сценарий | Latency (p95) | Guarantees |
|----------|---------------|------------|
| **TGN доступен** | < 200 мс | Риск-скор финальный |
| **TGN недоступен** | < 50 мс | Риск-скор предварительный (LightGBM only) |
| **TGN восстановлен** | < 5 мин | Риск-скор обновляется |
| **Обе модели недоступны** | — | FAIL-CLOSED: транзакция холдится |

## 6. OpenSanctions Data Risks

### 6.1. Актуальность данных (Data Freshness)
- **Риск**: Датасет OpenSanctions обновляется hourly; текущий час может не быть доступен еще
- **Смятие**: Кэш инициализируется из ранее scraped внешних меток; fallback к последнемуKnownGood timestamp
- **Влияние**: Модели работают с последknown данными; задержка в 1 hour максимум

#### 6.2. Покрытие адресов (Address Coverage)
- **Риск**: Из 1.2M+ сущностей OpenSanctions извлечено 148 крипопо кошельков (CryptoWallet schema)
- **Смятие**: Features применяются только к адресам, matching `0x...` (Ethereum) или `bc1...` (Bitcoin) паттерны; risk_score defaults to 0.5 для unknown addresses
- **Влияние**: 148/1.2M ≈ 0.012% от сущностей; но эти 148 address имеют высокий risk_score (0.7 default), обеспечивая значимый сигнал

#### 6.3. Ложные срабатывания (False Positives)
- **Риск**: Легитимные адреса могут совпасть с OpenSanctions паттернами по совору
- **Смятие**: Confidence-weighted integration (0.7 weight, а не hard exclusion); Unified Scorer комбинирует с 3 другими сигналами (LGBM 0.50, K-Score 0.20, VAE 0.15), смяляя эффект любого одиночного ложного срабатывания

#### 6.4. Предвзятость датасета (Dataset Bias)
- **Риск**: OpenSanctions фокусируется на санкционированных сущностях; может не покрывать все паттерны нелегальной активности
- **Смятие**: External signal является лишь 0.15 от 4-signal Unified Scorer; другие сигналы (LGBM 0.50, K-Score 0.20, VAE 0.15) обеспечивают broader coverage

#### 6.5. Temporal Drift
- **Риск**: Temporal split (t=37-44 val, t=45-49 test) может обнаружить drift, если OpenSanctions dataset significantly обновляется между валидацией и тестированием
- **Смятие**: Hourly refresh cycle ensures data doesn't change drastically within evaluation windows; temporal split all same hour (t=20260905xxx)
